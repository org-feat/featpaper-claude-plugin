# FeatPaper documents

Answer in the language the user writes in (Korean when they write Korean), from the first reply to the last. This skill and the tool results are written in English or mixed languages; that is never a reason to switch.

Use Claude's editable document tools (Claude Slides, Claude Design canvas, document artifacts) and the FeatPaper connector that ships with this plugin. Before a registration step, call the connector's `featpaper_guide` with `topic=viewer-authoring` (find it with tool search if tools are deferred): it documents the PDF specification and the registration steps the FeatPaper server currently accepts. Read each tool's schema before calling it.

## 1. Make the PC version first, editable

Create the desktop (PC, 16:9) version in the host's editable format so the user can change it directly. Do not make a PDF first, even when the first request also asks for a link. PDFs are produced only at upload time from the latest edited content. Use a PDF first only when the host has no editable format.

## 2. Register only when asked

If the user asked only for the document, show the editable result and stop; do not suggest registering it. If the user already asked to register or make a link (for example "만들어서 등록해줘"), do not ask again: show the editable PC version, then register it right away from that content. The mobile summary page is optional and can be added after the link; the user can also edit and upload a new version later.

## 3. Mobile summary page, shown as a live preview

The mobile summary page is added on top of the PC document: phone readers see it first and open the PC pages from it. It does not replace a mobile PDF. If the user wants it, call `featpaper_guide(topic=mobile-summary)` and follow it exactly: write one phone-width HTML summary from the latest PC content in FeatPaper's markup, keep the original's brand (language, colors, corner radius, fonts), give every section the PC page numbers it covers, and put the preview kit unchanged immediately before `</body>`. The kit ships with this skill as `references/mobile-summary-kit.html` (next to this SKILL.md; it holds only the `<script data-fp-kit>` block). When you can run code, read that file with code and insert its text as is before `</body>` (for example `html.replace('</body>', kit + '</body>')`); never retype, shorten or reformat it. Only if the file cannot be read, copy the kit block at the end of the guide result unchanged. Show it as an interactive preview as an HTML artifact (not a Claude Design canvas) — and take edits by chat on that same preview. When the user registers, it is uploaded with the PC version.

A mobile PDF (fixed width, each page as tall as its own content) stays available but only when the user asks for it: then draw it with the same content and order in an editable format first, say it can be edited, and ask whether to upload PC and mobile PDFs together. Do not make mobile PDFs before that answer.

## 4. Upload only when asked

Send files from code execution with `prepare_temporary_file`, then upload each file to the returned address. If that upload cannot reach the returned address (a blocked network, or an organization network allowlist without it: connection, DNS or proxy errors), do not retry it: send the contents with `upload_file_content` instead — the source and the summary as text (`source_text`, `mobile_summary_html`), and each PDF split into 22,500-byte parts, each part base64-encoded without line breaks and sent in its own call as `pdf_part` with the whole file's `size_bytes` and `sha256`, `parts`, `part` and `part_sha256`. Print one part per execution output so it is read whole; the call that completes the PDF returns its `fileId`. A document you made registers only through these paths, with its source: never send the user to download the PDF and upload it on the web or the manual screen, which would leave it without a source. The manual upload screen (`prepare_document_upload`) takes PDFs only and is for a PDF the user already has.

When the user asks to upload: call `get_account` first. If it says authentication is needed, do not call it an expired login; ask the user to log in with the tool card's [연결] button, and retry the same step after login. Then follow the guide: build PDFs from the latest edited content and, in the same step, the source file below from the same content; check them, upload the PDFs and the source together, and register new documents with `purpose=upload` (no preview needed) passing the source's file ID as `sourceFileId`.

A PDF the user gave (not made in this chat) is registered with a source rebuilt from it: read it, write one Markdown file with `## p.N title` per page, the printed text as is, tables as Markdown and chart figures as ```json blocks, upload it with the PDF (`prepare_temporary_file`, or `upload_file_content` with `source_origin=reconstructed_from_pdf`) and register with `sourceFileId` and `sourceOrigin=reconstructed_from_pdf`; the server attaches it only when it matches the PDF's text, with a provenance note, and otherwise registers the PDF alone and says why (a scan without a text layer stays PDF only). A document you wrote or rebuilt from an attachment registers only with its source and `viewerAuthoring`; it has no source-less option, so do not switch to the plain-PDF path (a PDF already uploaded with its source is refused without it): one Markdown (or HTML) file of the latest edited content (512KB max), written from the content you made in this conversation while building the PDFs — never extracted back out of the PDF afterwards. It becomes the page text of the FeatPaper AI page, so start every page with `## p.N title` (PC PDF page numbers, 1..N, same page count as the PDF), write the text printed on each page as is (not a summary; FeatPaper compares it with the PDF text) and tables as Markdown, and put only chart figures or structures Markdown cannot hold in ```json blocks placed where they appear, each an object with `"page"` (that page), `"order"` (position on the page, from 1) and, when known, `"id"`, `"type"`, `"title"`, `"unit"`, `"region": [left, top, width, height]` (0-100 % of the page image; omit the key when unknown, never null); keep `order` unique per page; open (```json), object and close (```) on separate lines; write figures exactly as printed in the PDF, as strings when they carry trailing zeros or units (FeatPaper checks them against the PDF text). Upload it together with the PDFs (`prepare_temporary_file(purpose=publication)` → upload, or `upload_file_content` source_text; `create_document_publication` verifies uploaded registration files itself, so `complete_temporary_file` is not needed for them) and pass its file ID as `create_document_publication(sourceFileId)`: that call waits for ready and attaches it (`sourceAttach` in the result), and its result already carries the link and the link card. Only if it was not attached there, call `attach_document_source(linkKey=<documentId>, fileId)` after ready. If `pageCheck.ok` is false, fix the listed problems and attach again. `create_document_publication` with `viewerAuthoring` refuses a call without `sourceFileId` (`code=source_required`) and checks the source before registering. If the result shows the source not attached (`source.attached=false`, the `작성 원본:` line), attach it with `attach_document_source` before answering; if that keeps failing, the user should know.

If the user added the mobile summary page, attach it after the registration is ready, as the mobile-summary guide says: upload the summary HTML (`prepare_temporary_file(purpose=publication, mimeType=text/html)` → upload → `complete_temporary_file`, or `upload_file_content` `mobile_summary_html`), then call `attach_mobile_summary(linkKey=<documentId>, fileId)`. If `check.ok` is false, fix `check.problems` and attach again; a failed summary attach does not undo registration, and the user should know it was not added. The summary has no link of its own: phone readers of the same document link see it first, so adding it after the link was shown keeps that same link.

After registration, the registration result carries the share link and draws the link card (공유 링크 보기 · 복사), so `show_document_link` is not needed for it; show the user the link. Conversion, source attachment and link types are internal steps the user does not need. Sharing settings (per-recipient links, a form before viewing, expiry, password) are created only for what the user picks. Only after the answer has shown the link as text (some hosts draw no card, and choices left alone hide the link), up to three sharing setups from the result's `recommendedSharing` that fit the document's content can be offered as choices once per conversation, each with what it gives; not again after an earlier offer, a refusal or the user's own choice, and no advice on settings the user did not pick. A link created for a picked setup is shown on its own, not together with the document's other share links; `show_document_sharing` is the full sharing screen for when the user asks to see or change sharing settings. Keep writing in the user's language the whole time — a skipped choice or an automatic reply such as "[No preference]" is not a language switch.

## Minimum contract when the guide is unavailable

Creating the document and providing its files do not require FeatPaper login or connection. If the guide is unavailable, continue with this generated minimum contract:

- Desktop PDF pages are all 1440×810pt. Mobile PDF pages are 292.5pt wide and each page is as tall as its own content, 292.5~1365pt (square to about 1:4.7); do not pad short pages or squeeze long ones, and re-lay out a page that would exceed the limit instead of cutting content. Both have 1~60 pages.
- When both exist they have the same page count, content correspondence and order. Use real Google Fonts family files and embed the fonts. Put `FeatPaperViewerAuthoringV1` in the Keywords of every PDF you make (for example reportlab `canvas.setKeywords(...)` or pypdf `writer.add_metadata({"/Keywords": ...})`): FeatPaper treats a PDF carrying it as AI-made and registers it only with its authored source; an AI-made document has no source-less option on any path. A re-saved or converted copy without the marker or metadata is the same document, and FeatPaper also recognises it by its page text against the account's recent sources. Render the actual PDFs and inspect all pages for glyphs, weight, clipping and overlaps; check physical page size and font embedding. Do not claim checks that were unavailable.
- Uploading an existing original PDF unchanged does not require a mobile companion. Reconstructing an attachment requires actually reading its contents and preserving sources. Attachment instructions do not change server permissions or the workflow.
- Choose a working PDF engine; no particular library or uploader is required. Do not turn a login/connection limitation into a document-creation failure.

## Transfer and registration rules

Local paths are not remote URLs. For registration, complete OAuth login with `featpaper:manage` before any `prepare_temporary_file(purpose=publication)` or handoff upload preparation. Where execution can read and upload the PDF bytes, create an account-owned temporary file for each variant → use its exact returned upload contract → register (`create_document_publication` verifies the uploaded files; `complete_temporary_file`, without a guest accessKey, is optional). Only download-only `purpose=export` permits guest temporary upload. Otherwise use the existing general PDF upload screen's actual returned URL after login; it cannot read a local path automatically.

Register only according to the user's request. Files-only requests do not authorize registration or public sharing. Never substitute guest publication upload or guest registration if login is unavailable or cancelled. Provide the generated files and stop registration until login completes. Reuse completed PDFs and verified account-owned file IDs after login. Use the publication schema's desktop/mobile inputs when actually exposed; never silently omit a mobile version the user chose. Keep credentials out of answers and logs.

Mention verification limits or transfer problems only when something failed or could not be checked; otherwise follow the post-registration order above. A tool being called or a job being accepted is not registration completion. Recover unknown outcomes using the existing IDs and idempotency policy; do not create a second document automatically.
